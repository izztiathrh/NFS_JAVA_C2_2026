## Fixing the 405 on POST /api/v1/tickets

User reported the create form now styles beautifully but submitting returned
"Failed to create ticket (HTTP 405)". Root cause: `vite.config.js` only had a
dev-server proxy. `npm run preview` (or any other static server) sent
`POST /api/v1/tickets` back to its own origin, which had no POST handler.

### Files

- New: `support-desk-api/.../config/WebConfig.java` — `WebMvcConfigurer` that
  opens CORS for `localhost:5173/4173` and `127.0.0.1:5173/4173` on
  `GET/POST/PUT/DELETE/OPTIONS/PATCH` for `/api/**`, with credentials and a
  1h preflight cache.
- Updated: `support-desk-api/.../exception/GlobalExceptionHandler.java` —
  added handlers for `MethodArgumentNotValidException` (returns a flat
  `field message; field message;` string) and
  `HttpRequestMethodNotSupportedException` (returns the supported methods
  list). Both keep the `ErrorResponse { message }` shape so the frontend
  helper can surface them.
- Updated: `support-desk-ui/vite.config.js` — added the same proxy block to
  `preview` so `npm run preview` (4173) forwards `/api` → `localhost:8080`.
- Updated: `support-desk-ui/src/api/tickets.js` — `readErrorMessage` now
  falls back to `response.text()` (trimmed to 300 chars) when the body isn't
  JSON, so future 4xx/5xx pages show the real reason instead of a bare
  `(HTTP 405)`.

### To apply

Backend needs a rebuild + restart (Maven wrapper not working in this
sandbox env, but the code is straightforward Spring). Once restarted, the
helper will show the backend's `message` instead of the status-only
fallback.

## Stale backend → 405 even though the JAR had the right method

User kept seeing `405 Method Not Allowed` on `POST /api/v1/tickets` even
after the CORS / proxy / handler fixes landed. Diagnosis:

- `OPTIONS /api/v1/tickets` returned `Allow: GET,HEAD,OPTIONS` (no POST)
  while `OPTIONS /api/v1/tickets/T001` returned `GET,HEAD,PUT,OPTIONS`
  (PUT worked). Spring had only the GET handlers registered for the
  exact path.
- The JAR at `target/support-desk-api-0.0.1-SNAPSHOT.jar` (built 14:41)
  DID contain a `createTicket` method with `@PostMapping` per `javap`.
- The running process (PID 29832) had been started **before** the
  `@PostMapping` was added and never restarted — it held the old class
  in memory, while later builds produced a fresh JAR.

Fix: `taskkill /F /PID 29832`, rebuild, restart.

### The Maven launcher bug in this sandbox

`mvn` from `C:\apache-maven-3.9.9\bin` fails with
`Could not find or load main class org.codehaus.plexus.classworlds.launcher.Launcher`
because the `mvn` script hard-codes a wrong class. The actual launcher
class in `boot\plexus-classworlds-2.8.0.jar` is `org.codehaus.classworlds.Launcher`.
Workaround:

```bash
java -classpath "C:\apache-maven-3.9.9\boot\plexus-classworlds-2.8.0.jar" \
     "-Dclassworlds.conf=C:\apache-maven-3.9.9\bin\m2.conf" \
     "-Dmaven.home=C:\apache-maven-3.9.9" \
     "-Dmaven.multiModuleProjectDirectory=<project>" \
     org.codehaus.classworlds.Launcher <goals>
```
